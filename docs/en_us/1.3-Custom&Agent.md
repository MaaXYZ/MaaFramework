# Custom & Agent

## Custom

Custom is an extension mechanism provided by the framework, allowing developers to implement special requirements that cannot be fulfilled by the built-in recognition algorithms and action types.

1. Custom Recognition

    When the built-in recognition algorithms (such as TemplateMatch, FeatureMatch, OCR, etc.) cannot achieve specific image recognition needs, you can use custom recognition methods.

2. Custom Action

    When the built-in action types (such as Click, Swipe, InputText, etc.) cannot fulfill specific operational needs, you can execute custom actions.

There are two mainstream approaches to writing Custom:

- For registering Custom via UI, please refer to the respective UI manual.

- For registering Custom via Agent, please refer to: [Agent](#agent) (⭐ Recommended)

For calling Custom in Pipeline, please refer to [Task Pipeline Protocol](3.1-TaskPipelineProtocol.md).

## Agent

When you need custom recognition or custom actions that are difficult to implement with Pipeline, Agent provides a more robust extension approach.

- **Improves stability**: Custom code is isolated from the framework core, reducing the risk that custom logic failures affect the whole process.
- **Easier to extend**: Suitable for complex business logic that needs independent iteration.
- **Easier to maintain**: Keeps a clearer boundary between framework upgrades and custom implementations.
- **Multiple language support**: You can choose the programming language that suits you and leverage its native features.

### AgentClient and AgentServer

#### AgentServer

AgentServer is used to register and execute your custom recognition and custom action code. It is commonly used to implement more complex *recognition decisions* or *business actions*, and to implement *event listeners*. It focuses on business capability itself rather than main-flow scheduling or framework lifecycle management.

A simple AgentServer example can be found in this [template commit](https://github.com/MaaXYZ/MaaPracticeBoilerplate/commit/126a56cefc17bf6c8335c703387d8d3ee2dad4d1).

#### AgentClient

AgentClient is part of the [UI](./1.2-ExplanationOfTerms.md), and is responsible for communicating with AgentServer. When the main flow reaches a custom node, AgentClient sends the request to the Server, receives the result after execution on the other side, and then brings the result back to continue the main flow. It bridges the invocation chain, but does not carry concrete business rules itself.

### When do you need to write Agent?

#### When do you need to write AgentServer?

> [!NOTE]  
> In common context, if not specifically stated, "Agent" in discussions usually refers to AgentServer.

It is usually recommended in the following scenarios:

- Custom recognition/action logic is complex, and implementing it with Pipeline is cumbersome.
- Custom recognition/actions require special logic or algorithms that cannot be implemented with Pipeline.

#### When do you need to write AgentClient?

> [!WARNING]  
> AgentClient is handled by the [UI](./1.2-ExplanationOfTerms.md). In most cases, you do not need to implement it yourself.

If you think the existing [Generic UI](/README_en.md#generic-ui) cannot meet your needs and you need to write a new generic UI yourself, then AgentClient is a required part.

## Custom controllers

A device with its own screenshot or input API can expose that API through a MaaFramework controller. The host creates the controller by name, calls `post_connection()` to connect the device, and binds it with `tasker.bind(resource, controller)`. Existing Pipeline recognition and actions such as `Click` then use the device.

### Providing a device through an Agent

Each registered name identifies one device instance in the Agent process. The host connects to the Agent over IPC or local TCP, lists the devices advertised for that session, and creates a proxy by name. Proxies for the same name share the server-side device state. Controller requests use a dedicated channel, so an action in the same Agent can wait for input or a screenshot. A controller-only Agent can connect directly. If the Agent also provides custom recognitions or actions, the host must call `client.bind(resource)` before connecting so they can be registered on that resource.

Save this Agent as `controller_agent.py`. It exposes an in-memory canvas that turns a pixel white when clicked. Returning 0 from `get_features()` directs the framework to call `click` directly. For a physical device, implement `screencap` and `click` using the device SDK.

```python
import sys

import numpy as np
from maa.agent.agent_server import AgentServer
from maa.controller import CustomController


@AgentServer.custom_controller("canvas")
class Canvas(CustomController):
    def connect(self):
        self.frame = np.zeros((720, 720, 3), dtype=np.uint8)
        return True

    def request_uuid(self):
        return "canvas-1"

    def get_features(self):
        return 0

    def click(self, x, y):
        self.frame[y, x] = 255
        return True

    def screencap(self):
        return self.frame


if not AgentServer.start_up(sys.argv[1]):
    raise RuntimeError("Agent startup failed")
AgentServer.join()
AgentServer.shut_down()
```

Run this host script from a file alongside the Agent. The first capture establishes the coordinate mapping. The second verifies that the click reached the device. Keep the Agent connected while tasks are running. Create a new proxy after reconnecting.

```python
import subprocess
import sys
from pathlib import Path

from maa.agent_client import AgentClient

client = AgentClient()
client.set_timeout(10000)
server = Path(__file__).with_name("controller_agent.py")
child = subprocess.Popen([sys.executable, str(server), client.identifier])
try:
    assert client.connect()
    assert "canvas" in client.custom_controller_list
    controller = client.create_custom_controller("canvas")
    assert controller.post_connection().wait().succeeded
    assert controller.post_screencap().wait().succeeded
    assert controller.post_click(20, 30).wait().succeeded
    image = controller.post_screencap().wait().get()
    assert image[30, 20].tolist() == [255, 255, 255]
finally:
    if client.connected:
        client.disconnect()
    elif child.poll() is None:
        child.terminate()
    child.wait()
```

### Providing a device through a native plugin

The plugin runs in the host process. Define `MAA_PLUGIN_EXPORTS` when building the plugin, include `MaaPlugin/MaaPluginAPI.h` and `MaaFramework/MaaAPI.h`, and link against `MaaFramework`. Use the v1 plugin API (`GetApiVersion()` returns 1) and export both functions with C linkage.

```c
MAA_PLUGIN_API const char* GetCustomControllerName(void);
MAA_PLUGIN_API MaaController* CreateCustomController(const char* config_json);
```

The first function returns a stable, nonempty UTF-8 name such as `"PixelDevice"`. The second reads the plugin-specific JSON configuration and returns a new, host-owned controller on each successful call, or `NULL` on failure. A plugin that allocates device state can use `MaaCustomControllerCreateWithRelease` to associate its callback table, device pointer and release function with the controller. Existing event-only v1 plugins continue to load as before.

In the host process, load plugins before creating any Resource, Controller, or Tasker. After plugin shutdown, factories no longer accept requests to create controllers.

```python
from maa.controller import PluginController
from maa.tasker import Tasker

assert Tasker.load_plugin("./ControllerFixture.so")
assert "PixelDevice" in PluginController.list_names()
controller = PluginController("PixelDevice", {"device": "device-1"})
assert controller.post_connection().wait().succeeded
```

This example uses the framework’s `ControllerFixture` test plugin. Substitute the actual library path for your platform. Each plugin defines its own configuration fields.
