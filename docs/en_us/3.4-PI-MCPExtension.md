# 3.4 Optional PI MCP Extension

**💡 PI v2.12.0**

This extension specifies how a [ProjectInterface V2](3.3-ProjectInterfaceV2.md) Client exposes project tasks through the [Model Context Protocol (MCP)](https://modelcontextprotocol.io/specification/latest). Resource authors continue to write PI; the Client maps PI and its existing execution flow to MCP tools; AI tools connect as MCP clients.

## Scope and Enablement

The goal is to let AI discover existing project tasks, understand their options, run them at the user's request, and inspect or stop that run. MCP is an **optional Client capability**: Clients can fully support PI without this extension, and resource projects do not need to declare or implement an MCP server.

- No top-level `mcp` field is added. `interface_version: 2` and the existing schemas are unchanged. Resource configuration must not automatically enable the server or grant control permissions.
- The server is disabled by default and explicitly enabled by the user in the Client. Clients should let users control task execution and screenshot permissions separately. Disabled capabilities must be absent from `tools/list`, and permissions must also be checked on each call.
- Clients supporting this extension implement the six core tools below. Without execution permission, only the four query tools are exposed. `capture_screen` is independently optional and does not affect core conformance.
- Tabs, editable queues, and a separate Web server are not required. Ports, SDKs, frontend/backend bridges, and Client configuration file formats are not standardized.
- This version does not provide tools for persistent task-list editing, switching devices/resources, installation/updates, arbitrary Pipeline overrides, Shell, clicks, or swipes. Declared project tasks can still execute programs or operate devices; execution authorization should cover their normal startup flow, including `pretask` and Agent.

Task parameters apply only to this run and do not rewrite the user's saved task lists, options, or presets. Clients may expose other tools for those product features, but must not make them prerequisites for this extension.

## Transport and MCP Behavior

Use MCP initialization, protocol version negotiation, `tools/list`, `tools/call`, and error handling without defining another JSON-RPC protocol. Clients may offer stdio or Streamable HTTP. Connection instructions identify the transport and connection parameters; there is no ecosystem-wide fixed port.

HTTP servers listen only on loopback by default, validate the peer and Host, and validate Origin according to MCP transport security requirements. Unauthorized browser origins must be rejected. Authentication, authorization, and transport protection for nonlocal deployments are outside this version; changing the listener to all interfaces alone is insufficient for remote access. stdio must keep logs out of protocol output.

Each tool must provide an accurate `inputSchema`. Return JSON results in `structuredContent` and include the same object as compact JSON text in `content` for MCP clients that only read text. If `outputSchema` is declared, successful results must conform to it. Screenshots use MCP image content.

Tool names and machine fields are not translated. `label`, `description`, tool titles, and error messages may be localized; PI `$` strings should be resolved first. Descriptions, logs, and screenshots are data and must not confer additional permissions.

## Instances, Versions, and Identifiers

An `instance` is a configured Client execution context: a project, selected controller, target device, resource, and local parameters. It may correspond to a CLI configuration or UI tab; a graphical interface is not required.

| Field | Convention |
| --- | --- |
| `pi_mcp_version` | Version of the tool contract in this document, fixed to the string `"1.0"`; identified separately from the MCP transport protocol version and PI JSON major version |
| `instance_id` | Opaque nonempty Client-generated string; not reused during a server lifetime, invalid after the instance is removed, and regenerated after a server restart |
| `context_revision` | Opaque nonempty string; changes when the project/imports, controller or target-device configuration, resource, or local options, pre-tasks, or credentials affecting execution change |
| `run_id` | Nonempty Client-generated string for each accepted run; unique for the instance lifetime and distinct from MaaTaskId |
| `request_id` | Nonempty string generated by the MCP caller for one startup intent, used to deduplicate retries; distinct from the JSON-RPC message ID |
| `name` / `option_key` | PI `task.name`, `case.name`, input field `name`, and `option` keys; never display names or array indexes |

Every tool except `list_instances` requires an explicit `instance_id`. Never fall back to the focused or first instance, or another device. Instances distinguish projects even when they have the same `name`. Callers must rediscover instances after a server restart.

Each instance must provide an unambiguous parameter baseline for a given `task.name`; PI defaults may be used when it is not configured. Do not guess between UI queue entries with the same name. Return `configuration_required` when required parameters cannot be resolved. Parameter descriptions and startup validation must use the same rules, and baseline changes must update `context_revision`.

## Core Tools

Parameters in this table are required unless marked `?`. Object fields use snake_case; unknown parameters should be rejected. Query tools must not connect devices, start pre-tasks, load execution resources, or execute tasks.

| Tool | Parameters | Successful result and semantics |
| --- | --- | --- |
| `list_instances` | None | `{pi_mcp_version, instances}`; each instance contains `instance_id`, `project` (`name`, optional `label` / `version`), `controller` (PI `name` or `null`), `resource` (PI `name` or `null`), `context_revision`, boolean `connected` / `busy`, and `active_run_id` (string or `null`) |
| `list_tasks` | `instance_id`, `cursor?`, `limit?` | `{context_revision, tasks, next_cursor}`; PI tasks compatible with the current controller/resource; entries contain `name` and optional `label` / `description` / `group` |
| `describe_task` | `instance_id`, `task_name`, `option_key?`, `cursor?`, `limit?` | `{context_revision, task_name, root_options, options, next_cursor}`; option descriptions defined below; only the specified option is returned when `option_key` is present |
| `start_tasks` | `instance_id`, `context_revision`, `request_id`, `tasks` | `{run_id, state}`; `tasks` is a nonempty ordered array of `{name, option?}`; validate and accept a parameter snapshot, start asynchronously, and return the run identifier immediately |
| `stop_tasks` | `instance_id`, `run_id` | `{run_id, state}`; request that the specified run stop; may return `stopping`; a submitted stop request does not mean the run has stopped |
| `get_run_status` | `instance_id`, `run_id`, `after?`, `limit?` | `{run_id, state, tasks, logs, next_cursor, logs_truncated, error?}`; inspect a specific run, including startup failures |

`list_tasks` returns tasks in merged PI order and includes only PI `task` declarations. `pretask` is handled by normal startup rather than exposed as an ordinary task; Client-specific special tasks are not mixed in.

`busy` includes startup, execution, and stopping initiated through other Client entry points. `active_run_id` identifies the current run queryable through this extension, or `null` if none exists. This extension does not require creating run records for other entry points, so `busy: true` and `active_run_id: null` may coexist; new starts must still be rejected.

For pagination, `limit` is an integer in `1..100`, default `50`. `cursor` is an opaque string and `next_cursor: null` indicates completion. Cursors are bound to the instance, query parameters, and context revision. A changed revision or invalid cursor returns `stale_context` so the caller restarts enumeration; never silently omit entries. Pagination in `describe_task` applies only to the cases of a specified `option_key`; `cursor` must not be supplied without that key.

## Option Descriptions and Parameters

`root_options` is the task's `task.option` key array. `options` is a description table indexed by key, with each applicable option reachable from the task appearing at most once; do not recursively duplicate the entire tree. Controller/resource filtering follows PI rules.

An option description contains `type` (including PI's default `select`), optional `label` / `description`, the redacted baseline `value`, and the following type-specific fields:

- `select` / `switch` / `checkbox`: `case_count`; `checkbox` also includes declared `min_count` / `max_count`. Omit `cases` by default; when `option_key` is specified, return paginated `cases`, each with `name`, optional `label` / `description`, and the child-option key array `option`. Labels cannot replace `case.name`.
- `input`: `inputs`, retaining each field's `name`, `label`, `description`, `pipeline_type`, `verify`, `pattern_msg`, `password`, `input_type`, and non-password `default`.
- `hotkey`: `hotkeys`, retaining PI field descriptions and string defaults.

A specified `option_key` must be reachable through the task's root options and case child options. It cannot be used to read unrelated project options. Case references contain keys only; cycles must not cause infinite expansion. `next_cursor` is `null` when there is no case pagination.

`start_tasks.tasks[].option` uses the PI `preset.task[].option` value format:

| Type | Value |
| --- | --- |
| `select` / `switch` | A `case.name` string; switches use the actual declared Yes/No case names rather than a separate boolean conversion |
| `checkbox` | An array of distinct `case.name` strings; overrides still follow PI `cases` declaration order |
| `input` | An object mapping field `name` to a string; send strings even when `pipeline_type` is `int` / `bool` |
| `hotkey` | An object mapping hotkey field `name` to a hotkey string, not virtual key codes |

Start from the baseline values in `describe_task`. Omitted options and input fields retain baseline values. Supplied select/switch/checkbox values replace their baseline values; input/hotkey objects merge by field. Child options use their own keys in the same `option` object rather than nesting inside the parent value.

Clients must construct the complete candidate parameters before computing child-option activation and validating the final selection, independently of JSON key order. Unknown tasks/options/fields/cases, mismatched types, duplicate checkbox values, count limits, regex or type-conversion failures, and explicitly supplied incompatible/inactive options reject the entire request without partial execution.

Global, resource, and controller options and pre-tasks use the instance's existing configuration; this tool does not modify them. Normal PI filtering, override priority, resource integrity checks, and Agent environment-variable conventions still apply.

### Password Fields

All results, including baseline values, field defaults, errors, and logs, must omit values of `password: true` fields while retaining their `password` marker. Do not return ciphertext or writable mask placeholders, or bypass this restriction through other raw PI / Pipeline data.

This version rejects setting password fields through MCP with `sensitive_option`; omission retains locally configured credentials. Return `configuration_required` for missing credentials needed by the run and direct the user to the Client's local configuration channel rather than asking for secrets in AI chat. Even invalid PI containing a password `default` must not expose it.

## Run Lifecycle

`state` has the following values:

| State | Meaning |
| --- | --- |
| `starting` | Accepted; preparing, running pre-tasks, connecting devices, or loading resources; the task sequence has not started |
| `running` | Executing the requested task sequence |
| `stopping` | Stop requested; cancelling startup or waiting for the current task to finish safely |
| `succeeded` | All requested tasks completed successfully; terminal |
| `failed` | Startup or task execution failed; terminal |
| `stopped` | Stopped, with no further task submissions or startup steps from this run; terminal |

All terminal states require startup and execution work for the run to have ended, with no background flow that can still submit tasks. Before orderly instance removal, stop and clean up its run rather than invalidating identifiers while work is still running.

### Acceptance and Startup

1. Within one critical section for the instance, check permissions, revision, tasks, and parameters, take an immutable snapshot, and register `run_id` before starting asynchronous work. Validation failure creates no run and no device/program side effects.
2. The snapshot includes the ordered tasks, complete effective parameters, pre-tasks, local credentials, and controller/resource configuration. Subsequent local edits must not change this run; later requests read the new revision.
3. Each instance allows only one run from acceptance until a terminal state. MCP, UI, hotkeys, and scheduled starts must share this restriction. Instances are independent: stopping A must not cause a stop request for B to be ignored.
4. Reuse the Client's normal permission checks, pre-tasks, connection, resource loading, and Agent flow, but execute the requested snapshot rather than silently substituting the UI's checked task list. MCP must not automatically elevate privileges; fail the run with a reason when additional user action is needed.
5. Execute `tasks` in array order with each entry's own `option`. The same task name may explicitly appear multiple times with different parameters. A failed entry prevents subsequent entries from starting and makes the run `failed`.
6. `start_tasks` does not wait for connection, resource loading, or task completion. Startup failures after acceptance remain queryable under the same `run_id`; they must not become untracked background work.

`context_revision` must match the current instance, otherwise return `stale_context`. Clients allocate revisions rather than deriving them from public hashes of passwords.

### Retries and Stopping

Deduplicate by `(instance_id, request_id)`: retrying identical startup parameters returns the same `run_id` and current state without executing again, even after completion. Reusing the identifier with different parameters returns `request_conflict`. Comparison ignores object key order but preserves array order.

Deduplication lookup must precede new revision/busy checks so a later context change does not turn a retry of an accepted request into a new request. Permissions are checked every time. Retain deduplication mappings, run identifiers, and terminal states for the instance lifetime; logs may have bounded retention. On reaching capacity, reject new starts with `resource_exhausted` rather than forgetting identifiers and allowing retries to execute again.

Stops target a `run_id`. Terminal runs return their existing terminal state; a stop for an old run cannot stop a later run in that instance. Stopping a `starting` run must cancel its subsequent startup steps rather than only stopping a Tasker that has not received tasks yet.

Report `stopped` only after startup has exited, relevant pre-task/execution work has ended, and no further tasks can be submitted. Remain `stopping` and allow polling when safe termination cannot be immediate; do not report stop success prematurely. Stopping cannot undo device actions or external program side effects that have already occurred.

Disconnection, tool timeout, or MCP request cancellation does not mean the run was cancelled. Recover the startup result with the same `request_id`, or query/explicitly stop the corresponding `run_id`; do not blindly retry with a new identifier.

Deduplication does not survive server restarts. When the old `instance_id` is invalid, rediscover instances and establish the earlier run's outcome rather than automatically replaying an uncertain startup request under a new instance identifier.

### Status and Logs

`get_run_status.tasks` returns `{index, name, state, option}` in request order. The zero-based `index` distinguishes repeated task names; `option` contains the snapshot's complete redacted task-level parameters. Entry states are `pending` / `running` / `succeeded` / `failed` / `stopped` / `skipped`; entries not executed because of startup/earlier failure or stopping are `skipped`. A failed run must include a redacted `error` as defined below.

Log entries are `{cursor, level, message}`, where `cursor` is an opaque string and `level` is `debug` / `info` / `warning` / `error`. `after` is a log cursor for the same run: omit it to read recent logs, or provide it to read later entries. `limit` defaults to `20` and ranges from `1..100`. `next_cursor` marks the position reached and is `null` before any logs exist. Set `logs_truncated: true` when retention has caused a gap rather than presenting the output as a complete record.

Clients should locally record MCP as the source of start/stop actions, instance/run identifiers, and task names without logging full requests, credentials, or screenshot contents. Log reads are limited to that run rather than exposing arbitrary file reads.

## Optional Screenshot Tool

Expose `capture_screen({instance_id})` only when the Client supports it and the user grants permission. Capture only the device already connected to that instance. Return `not_connected` otherwise; do not automatically connect or start tasks to obtain an image.

On success, return an MCP image block with MIME type `image/png` in `content`, alongside JSON text of the same result object. `structuredContent` is `{instance_id, captured_at, width, height}`. `captured_at` is an RFC 3339 timestamp with a time zone, and dimensions are pixels in the returned image. Do not return local file paths or put image base64 in JSON fields. The image is a live observation; do not claim exact synchronization with a log entry or node.

## Errors and Tool Hints

Business failures use MCP `CallToolResult` with `isError: true` and the JSON object `{error: {code, message, path?}}`. `get_run_status.error` uses the same inner object; querying a run that is `failed` is a successful status query. Unknown tools and invalid tool-parameter shapes use standard MCP protocol errors.

Stable error codes are `instance_not_found`, `task_not_found`, `option_not_found`, `invalid_option`, `sensitive_option`, `configuration_required`, `stale_context`, `instance_busy`, `request_conflict`, `run_not_found`, `not_connected`, `permission_denied`, `resource_exhausted`, and `execution_failed`. Optional `path` is a JSON Pointer, such as `/tasks/0/option/Stage/chapter`. Errors may describe valid case names or constraints, but must not echo passwords or full requests. Execution-stage failures use `execution_failed` or a more specific applicable code above.

Query tools should have `readOnlyHint: true`. `start_tasks` has `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: true`, and `openWorldHint: true`; idempotency depends on the required `request_id`. `stop_tasks` has `readOnlyHint: false`, `idempotentHint: true`, and `openWorldHint: true`. Annotations are hints rather than permission checks.

## Call Example

These examples show tool arguments or JSON results without repeating MCP envelopes. Assume the instance already has its controller, resource, and required local credentials configured.

Obtain an explicit target from `list_instances`:

```json
{
    "pi_mcp_version": "1.0",
    "instances": [
        {
            "instance_id": "instance-a",
            "project": {"name": "ExampleProject", "version": "1.0.0"},
            "controller": "Android",
            "resource": "Official",
            "context_revision": "revision-7",
            "connected": false,
            "busy": false,
            "active_run_id": null
        }
    ]
}
```

After calling `list_tasks` and `describe_task`, start a run with the actual task name and options:

```json
{
    "instance_id": "instance-a",
    "context_revision": "revision-7",
    "request_id": "client-intent-42",
    "tasks": [
        {
            "name": "FarmStage",
            "option": {
                "Mode": "Manual",
                "Stage": {"chapter": "4"},
                "Features": ["AutoBattle", "Collect"]
            }
        }
    ]
}
```

`start_tasks` returns after acceptance:

```json
{"run_id": "run-12", "state": "starting"}
```

Poll `get_run_status`; to stop, call `stop_tasks` on the same run. Both tools have these minimum arguments:

```json
{"instance_id": "instance-a", "run_id": "run-12"}
```

## Reference and Design Choices

Task discovery, preset-format parameters, and screenshots draw on [MXU #414](https://github.com/MaaXYZ/MXU/pull/414). This contract does not claim compatibility with its existing interface:

| Reference feature | PI decision |
| --- | --- |
| Tabs and current focus | Explicit execution instances without a UI dependency |
| Adding/editing/removing task-list entries | Submit one run snapshot; no particular queue or persistent configuration model is required |
| MXU special tasks and runtime appends | Outside the core; execute PI-declared tasks only, with a fixed sequence after acceptance |
| Waiting synchronously for startup and returning stop booleans | Run identifiers and explicit states cover stopping during startup, timeouts, and retries |
| Screenshots | Independent support and permission rather than a prerequisite for core functionality |
