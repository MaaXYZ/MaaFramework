# 2.2 Integrated Interface Overview

## About Binding

Different language bindings may have different naming conventions and are wrapped according to the [Standardized Interface Design](./4.2-StandardizedInterfaceDesign.md). Please search for the actual names yourself. Some interfaces may be used automatically internally and not provided directly (such as StringBuffer-related interfaces). Below are reference names for some interfaces across different bindings.

| C API                                             | Python Standard Interface         | NodeJS Standard Interface         |
| ------------------------------------------------- | --------------------------------- | --------------------------------- |
| MaaVersion()                                      | Library.version()                 | Global.version                    |
| MaaTaskerCreate()                                 | Tasker()                          | new Tasker()                      |
| MaaTaskerDestroy(tasker_handle)                   | Called automatically on destruct  | tasker.destroy()                  |
| MaaResourcePostBundle(res_handle, path)           | resource.post_bundle(path)        | res.post_bundle(path)             |
| MaaControllerPostClick(ctrl_handle, x, y)         | controller.post_click(x, y)       | ctrl.post_click(x, y)             |
| MaaTaskerInited(tasker_handle)                    | tasker.inited                     | tasker.inited                     |
| MaaTaskerPostTask(tasker_handle, entry, override) | tasker.post_task(entry, override) | tasker.post_task(entry, override) |
| MaaImageBufferResize(image_handle, width, height) | ImageBuffer.resize(width, height) | Global.resize_image(image, width, height) |

    Set whether to save recognition results to `log path/vision`. When enabled, RecoDetail can retrieve draws.

### MaaResourceSetOption

Set resource options. Will be split into specific options in bindings.

- InferenceDevice  
    Set inference device.

- InferenceExecutionProvider  
    Set the inference execution provider:

    - `Auto`: try CUDA, then DirectML, then WebGPU, then CoreML, and fall back to CPU
    - `CPU`
    - `DirectML`: Windows. `InferenceDevice` is the Win32 `EnumAdapters1` adapter id
    - `WebGPU`: Windows, Linux and macOS. `InferenceDevice` is the WebGPU device id; `Auto` uses device 0
    - `CUDA`: `InferenceDevice` is the NVIDIA GPU id. The current prebuilt packages do not include CUDA
    - `CoreML`: deprecated. MaaDeps no longer ships CoreML; use WebGPU. The value is kept so existing callers still compile
    - `NCNN`: Android only (setting it fails on other platforms), CPU only (`InferenceDevice` must be `CPU` or `Auto`, other values fail the loading), never picked by `Auto`. Models are loaded from `<stem>.ncnn.param/.ncnn.bin/.ncnn.json` next to the `model` path (the .onnx file is not needed). **There is no fallback to onnxruntime**: a missing or broken ncnn model fails the recognition, so ship ncnn models together with this provider. OCR also runs on NCNN, loading `det.ncnn.param/.bin`, `rec.ncnn.param/.bin` and `keys.txt` from the OCR model dir, with no fallback either. `<stem>.ncnn.json` carries what the ncnn files do not:
        - `input_shape` (required): fixed NCHW input shape, batch must be 1, e.g. `[1, 3, 640, 640]`
        - `input` / `output` (optional): input / output blob names, default to the first input / output of the `.ncnn.param`
        - `metadata` (optional): string-valued map, equivalent to the onnx custom metadata, e.g. `"names": "{0: 'cat', 1: 'dog'}"` for detector labels
        - `options` (optional): fp16 options of the model, see below

        OCR may ship optional `det.ncnn.json` / `rec.ncnn.json` next to the models. Only their `options` is read, the input size and pre / post processing follow fastdeploy PP-OCR.

Both options should be set before loading resources. A change made after loading starts (any `MaaResourcePost*`) is applied on the next `MaaResourcePost*`, and only to models that are not loaded yet; call `MaaResourceClear` and load again to switch every model. Switching to or from `NCNN` changes the inference engine and the model files, so it fails once loading starts until `MaaResourceClear` is called or the resource is recreated.

**NCNN `options`**: only the precision of a model is configurable, using the fp16 fields of `ncnn::Option`:

| Key | Type | Default | Description |
| --- | --- | --- | --- |
| `use_fp16_packed` | bool | `false` | fp16 packed layout |
| `use_fp16_storage` | bool | `false` | Store weights and intermediate blobs in fp16 |
| `use_fp16_arithmetic` | bool | `false` | Compute in fp16 |

MaaFW runs ncnn in fp32 by default so that the scores match onnxruntime. fp16 is faster on ARMv8.2+ CPUs at the cost of precision, enable it per model (usually all three together) after checking its results. Device related options are handled by MaaFW and are not configurable: the thread count is the number of big + middle cores (at most 4), the others keep the ncnn defaults. Unknown keys are ignored with a warning, a non-boolean value fails the model. For example:

```json
{
    "input_shape": [1, 3, 640, 640],
    "options": { "use_fp16_packed": true, "use_fp16_storage": true, "use_fp16_arithmetic": true }
}
```

### MaaControllerSetOption

Set controller options. Will be split into specific options in bindings.

- ScreenshotTargetLongSide  
    Set screenshot scaling long side to specified length

- ScreenshotTargetShortSide  
    Set screenshot scaling short side to specified length

- ScreenshotTargetExpand  
    Scale screenshots to a reference resolution `(width, height)` using Unity Canvas Scaler **Expand** semantics: `scale = max(width / raw_width, height / raw_height)`. The scale is applied uniformly to both axes so the source aspect ratio is preserved and both output dimensions are >= the reference. No cropping, no non-uniform stretching. Mutually exclusive with `ScreenshotTargetLongSide` / `ScreenshotTargetShortSide`; setting any of them resets the others. Value is an `int32_t` array of length 2: `{ width, height }`.

- ScreenshotUseRawSize  
    No scaling for screenshots

- ScreenshotResizeMethod  
    Set screenshot resize interpolation method (0=INTER_NEAREST, 1=INTER_LINEAR, 2=INTER_CUBIC, 3=INTER_AREA, 4=INTER_LANCZOS4), default is INTER_AREA(3)

- BackgroundManagedKeys  
    Declare Win32 background managed key domain. After setting, matching `MaaControllerPostClickKey`, `MaaControllerPostKeyDown`, `MaaControllerPostKeyUp` and pipeline `ClickKey`, `LongPressKey`, `KeyDown`, `KeyUp` operations automatically route through the background guardian path. Only supported by Win32 controllers; other controllers will fail.

### MaaControllerPostScroll

- `dx`: Horizontal scroll distance, positive values scroll right, negative values scroll left
- `dy`: Vertical scroll distance, positive values scroll up, negative values scroll down

Asynchronously scroll. This is an asynchronous operation that immediately returns an operation id. You can query the status via `MaaControllerStatus` and `MaaControllerWait`.

> [!NOTE]
>
> - Win32, macOS, and custom controllers that implement `scroll` support scroll operations.
> - Posting scroll to a controller that does not implement `scroll` will cause the action to fail.
> - The `dx`/`dy` values are sent directly as scroll increments. The Windows standard wheel increment is 120 (WHEEL_DELTA) per notch. Using multiples of 120 is recommended for best compatibility.

### MaaControllerPostInactive

Asynchronously set the controller to inactive state. For Win32 controllers, this restores the window's topmost status, unblocks input, restores cursor/window positions, and reverts other invasive operations. Other controllers perform no operation. This is an asynchronous operation that immediately returns an operation id. You can query the status via `MaaControllerStatus` and `MaaControllerWait`.

> [!NOTE]
>
> The Tasker automatically calls this after all tasks finish, so manual invocation is usually unnecessary.

## MaaToolkitIOSDevice.h

Provides iOS discovery, pairing, connection checks and DDI preparation. `Discover`, `Pair`, `CheckConnection` and `Prepare` are synchronous and return `MaaBool`. The caller creates `result` with `MaaStringBufferCreate`; it receives JSON containing `success`, `cancelled` and `error`, including on failure.

- `connection_method`: `MaaIOSConnectionMethod_Auto`, `USB` or `WiFi`. Auto discovery scans both transports. For pairing, connection checks and DDI preparation, Auto prefers the target's physical USB connection, otherwise Wi-Fi.
- `options_json`: operation options as a JSON object; pass `NULL` for defaults. Unknown fields fail validation.
- `event_callback`, `cancel_callback`, `userdata`: optional callbacks and caller data. Wi-Fi pairing requires an event callback to display its PIN. See [iOS device management callbacks](2.3-CallbackProtocol.md#ios-device-management-callbacks).

### MaaIOSWiFiPairing

Wireless credentials contain the device UDID, host identifier and peer identifier as NUL-terminated UTF-8 strings, three 32-byte signing-key arrays and an optional 16-byte peer IRK array. `has_peer_alt_irk` indicates whether the IRK is present.
UDID and host identifier accept 1–1024 UTF-8 bytes; peer identifier accepts 1–4096. Identity strings cannot contain NUL or line breaks.

`Pair` and `ParsePairingRecord` return owned objects; release them with `MaaToolkitIOSDeviceDestroyPairing`. Their string pointers remain valid until destruction. Inputs to device operations are copied before device I/O and borrowed only until the synchronous call returns. Controllers copy credentials during creation.

| Operation | Credentials |
| --- | --- |
| Discover / FindWithOptions | Array of credential pointers and count; at most 256 unique UDIDs |
| Pair | No input credential; returns a new pairing |
| CheckConnection / Prepare | One target credential with a matching UDID |

Auto prefers physical USB for the specified UDID, then paired Wi-Fi discovery. USB uses system trust and ignores wireless parameters. WiFi uses RemotePairing and requires credentials; an empty address enables mDNS discovery. Wi-Fi pairing advertises the host instead of connecting to a device address. Discovery can run without credentials, but cannot mark unmatched advertisements as paired.

### MaaToolkitIOSDeviceDiscover

- `wifi_pairings`: array of wireless credential pointers; may be `NULL` with count `0`
- `wifi_pairing_count`: at most 256 credentials with unique UDIDs
- `options_json`: `timeout_ms`, 0–60000, defaults to 3000 milliseconds; USB enumeration has a separate one-second budget
- `result [out]`: common status fields plus `usb_available`, `wifi_available`, `devices` and `warnings`

Returns a USB/Wi-Fi discovery snapshot without pairing, installing DDI or starting media. Each device has `udid`, `name`, `candidates` and `screencap_methods`. Candidates retain transport, address, port, interface and pairing state. Wireless credentials match advertisements; discovering an advertisement does not verify a connection.

`screencap_methods` reports backends available in this build. Device service support must be checked after connecting.

### MaaToolkitIOSDevicePair

- `udid`: target identifier; may be empty and returned in the pairing result. Specify it when several devices are candidates
- `options_json`: `timeout_ms`, 1–300000, defaults to 120000 milliseconds; `host_name` sets the Wi-Fi pairing advertisement name
- `result [out]`: common status fields and the paired device's `udid`
- `pairing [out]`: required output pointer; receives an owned `MaaIOSWiFiPairing*` on success or `NULL` on failure

Creates new RemotePairing wireless credentials. USB uses the system usbmux trust to establish a pairing channel. Wi-Fi advertises the host and sends a one-use code through a `pin` event for entry on the device. No existing credential is accepted.

The caller decides whether to persist credentials. String pointers remain valid until destruction; controller creation copies the fields. Release the output with `MaaToolkitIOSDeviceDestroyPairing`.

### MaaToolkitIOSDeviceParsePairingRecord

- `record`: a single-line credential string in the `MaaIOS1` format

Returns an owned `MaaIOSWiFiPairing*`, or `NULL` on failure. Does not contact the device or check whether the device has revoked the pairing.

### MaaToolkitIOSDeviceFormatPairingRecord

- `pairing`: structured credentials, including a valid caller-assembled structure
- `record [out]`: caller-created string buffer

Serializes credentials to a single-line `MaaIOS1` string and returns success. See [Pairing record format](#pairing-record-format) for the serialized fields and [MaaIOSWiFiPairing](#maaioswifipairing) for structure constraints.

#### Pairing record format

The optional persistence format is a single line with the `MaaIOS1` header. Fields are separated by `|`, without a trailing separator:

```text
MaaIOS1|udid=...|hid=...|pid=...|hsk=...|hpk=...|ppk=...|irk=...
```

| Field | Structure member |
| --- | --- |
| `udid` | `udid` |
| `hid` | `host_identifier` |
| `pid` | `peer_identifier` |
| `hsk` | `host_private_key` |
| `hpk` | `host_public_key` |
| `ppk` | `peer_public_key` |
| `irk` | `peer_alt_irk` (optional) |

Text values encode `%` as `%25` and `|` as `%7C`; key bytes use hexadecimal. Line breaks, duplicate fields, unknown fields and malformed escapes are rejected.
Formatting and parsing do not contact the device. Controllers and device operations accept the structure directly, without JSON or hex decoding.

PiCli saves credential strings in `ios.pairing_records` in `config/maa_pi_config.json`. It parses them when loading credentials, passes structures to device operations and formats them only when saving.

### MaaToolkitIOSDeviceDestroyPairing

- `pairing`: an object returned by `Pair` or `ParsePairingRecord`; may be `NULL`

Releases the object and its string storage. Do not use it to free caller-assembled structures.

### MaaToolkitIOSDeviceCheckConnection

- `udid`: required nonempty target identifier
- `wifi_address`: Wi-Fi address; empty or `"auto"` enables discovery
- `wifi_pairing`: one target credential with a matching UDID; required in WiFi mode. USB ignores wireless inputs
- `options_json`: `port`, 1–65535, defaults to 49152; accepted only with an explicit Wi-Fi address
- `result [out]`: common status plus `verified` and `session_open`; success also includes `udid`, `transport`, `os_version` and `product_type`

Establishes and verifies a connection, then closes it before returning; `session_open` is `false`. Does not transfer a session to a later controller or prepare DDI.

### MaaToolkitIOSDevicePrepare

Uses the same connection parameters as `CheckConnection`, including a required nonempty UDID.

Supported `options_json` fields:

| Field | Default | Meaning |
| --- | --- | --- |
| `port` | `49152` | Port for an explicit Wi-Fi address, 1–65535 |
| `cache_directory` | Empty | Temporary files are cleaned up; `"auto"` uses the platform user cache directory, or an explicit directory enables reusable persistent caching |
| `replace` | `false` | Allow replacement of an existing developer image |
| `download_timeout_seconds` | `300` | Download budget, 1–3600 seconds |
| `install_timeout_seconds` | `180` | Installation budget, 1–3600 seconds |

Selects, downloads and installs a DDI for the device OS and hardware, then verifies mounting. An existing image is reused when its suitability can be confirmed; an unverifiable image is not replaced by default. Downloading and device-specific ticket requests require access to their network services.

`result` contains the common status and `device_may_have_changed`. Successful `status` values are `already_mounted`, `mounted`, `already_installed` or `installed`; additional metadata depends on the executed path. Failure or cancellation does not guarantee rollback of device operations.

Omitting `cache_directory` uses a unique temporary directory, cleaned up after completion, failure or cancellation. An explicit directory enables reuse and revalidation across calls. An applicable mounted CoreDevice image with the screenshot feature can be reused without downloading. Classic images are reused without downloading when their mounted signature matches the pinned catalog for the device OS. A different or unverifiable Classic signature fails unless `replace` is explicitly enabled.

Toolkit does not choose a persistent cache directory. See [Automatic DDI preparation in PiCli](2.4-ControlMethods.md#automatic-ddi-preparation-in-picli) for PiCli defaults and preparation settings.

### iOS pairing examples

The C example assumes a suitable DDI is already mounted. The event callback displays PIN/progress events; see [iOS device management callbacks](2.3-CallbackProtocol.md#ios-device-management-callbacks) for callback ownership and cancellation.

```c
MaaStringBuffer* status = MaaStringBufferCreate();
MaaIOSWiFiPairing* pairing = NULL;
/* event_callback displays the PIN; see the callback protocol. */
if (MaaToolkitIOSDevicePair(
        NULL, MaaIOSConnectionMethod_WiFi, NULL,
        event_callback, NULL, NULL, status, &pairing)) {
    MaaController* controller = MaaIOSControllerCreate(
        pairing->udid, MaaIOSScreencapMethod_Default, MaaIOSConnectionMethod_WiFi, NULL, pairing);
    MaaToolkitIOSDeviceDestroyPairing(pairing);
    /* controller now owns a copy; connect with MaaControllerPostConnection. */
    /* Destroy the controller when finished. */
    MaaControllerDestroy(controller);
}
MaaStringBufferDestroy(status);
```

The Python example pairs, prepares the DDI with temporary downloads, discovers the device and creates a controller. `format_ios_pairing_record` is optional; after loading a saved string, restore the structure with `Toolkit.parse_ios_pairing_record(credential)`.

```python
from maa.toolkit import Toolkit
from maa.controller import IOSController
from maa.define import MaaIOSConnectionMethodEnum

# Print only the PIN/progress event, never the returned credential.
def on_event(event):
    print(event.get("pin", event.get("message", "")))
    return True

status, pairing = Toolkit.ios_pair(
    connection_method=MaaIOSConnectionMethodEnum.WiFi, on_event=on_event,
)
if not status["success"]:
    raise RuntimeError(status["error"])

# Optional persistence; pass the structure directly for device operations.
credential = Toolkit.format_ios_pairing_record(pairing)
status = Toolkit.ios_prepare(
    udid=pairing.udid, connection_method=MaaIOSConnectionMethodEnum.WiFi, wifi_pairing=pairing,
)  # Temporary downloads by default.
if not status["success"]:
    raise RuntimeError(status["error"])
devices = Toolkit.find_ios_devices(wifi_pairings=[pairing])
controller = IOSController(
    udid=pairing.udid, connection_method=MaaIOSConnectionMethodEnum.WiFi, wifi_pairing=pairing,
)
# After loading a saved string: pairing = Toolkit.parse_ios_pairing_record(credential)
```

>
> - On Win32, the returned value is a native `HWND`.
> - On macOS, the returned value represents the window `windowID` (`CGWindowID` / `SCWindow.windowID`). It is force-cast to `void*` at the API layer, so it is not a Cocoa `NSWindow*` pointer.
> - On Linux, the returned value represents the display number `n` in the Wayland socket name `wayland-<n>`. It is force-cast to `void*` at the API layer, so it is not a native window handle.

### MaaToolkitDesktopWindowGetClassName

- `window`: Window

Get window class name

> [!NOTE]
>
> - On Win32, the returned value is the window class name.
> - On macOS, the returned value is the Bundle ID (`SCWindow.owningApplication.bundleIdentifier`).
> - On Linux, the returned value is the full path of the Wayland socket (e.g. `/run/user/1000/wayland-0`).

### MaaToolkitDesktopWindowGetWindowName

- `window`: Window

Get window name

> [!NOTE]
>
> - On Win32, the returned value is the window name.
> - On macOS, the returned value is the window title (`SCWindow.title`).
> - On Linux, the returned value is the file name of the Wayland socket (e.g. `wayland-0`).

## MaaToolkitPortal.h

> Linux (non-Android) only; calls on other platforms fail and return empty values (`nullptr` / `-1` / `0` / `false`).

### MaaToolkitPortalHelperCreate

Create a Portal helper object, used to complete the authorization flow through the `xdg-desktop-portal` ScreenCast interface and obtain PipeWire screencap stream parameters.

### MaaToolkitPortalHelperDestroy

- `helper`: Portal helper object

Destroy the Portal helper object and close the D-Bus session it holds

### MaaToolkitPortalHelperOpenStream

- `helper`: Portal helper object

Run a complete ScreenCast authorization flow (CreateSession → SelectSources → Start → OpenPipeWireRemote), selecting a single monitor. A system authorization dialog pops up during the process and waits for user confirmation; it fails if not confirmed within 30 seconds.

> Authorization options must be set before calling via `MaaToolkitPortalHelperSetPersist` / `MaaToolkitPortalHelperSetRestoreToken`.  
> On failure, the session created internally during this call is cleaned up.

### MaaToolkitPortalHelperGetPersist

- `helper`: Portal helper object

Get whether persistent authorization (persist) is currently requested, default `false`

### MaaToolkitPortalHelperSetPersist

- `helper`: Portal helper object
- `enable`: whether to request persistent authorization

Set whether to request persistent authorization; must be called before `MaaToolkitPortalHelperOpenStream`

### MaaToolkitPortalHelperGetPipeWireFD

- `helper`: Portal helper object

Get the PipeWire socket FD obtained from authorization (`-1` means not yet obtained), usable as the `pw_socket_fd` config of the Linux controller

### MaaToolkitPortalHelperGetPipeWireNodeID

- `helper`: Portal helper object

Get the PipeWire node ID obtained from authorization (`0` means not yet obtained), usable as the `pw_node_id` config of the Linux controller

### MaaToolkitPortalHelperGetRestoreToken

- `helper`: Portal helper object

Get the restore token (empty string means not obtained). When persistent authorization is requested, the portal issues it after successful authorization; persist it and pass it next time via `MaaToolkitPortalHelperSetRestoreToken` to avoid repeated authorization

### MaaToolkitPortalHelperSetRestoreToken

- `helper`: Portal helper object
- `token`: restore token

Set the restore token; must be called before `MaaToolkitPortalHelperOpenStream`; passing a null pointer fails
