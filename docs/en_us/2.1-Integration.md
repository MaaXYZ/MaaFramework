### Resource loading diagnostics

`MaaResourceGetLoadDetail(resource, res_id, buffer)` retrieves a completed load's JSON snapshot. Python and Node.js expose `resource.get_load_detail(res_id)`. The return value indicates snapshot availability; `status` contains the existing `MaaStatus` load outcome. Unknown, unfinished and cleared IDs return false / None / null. A successful `MaaResourceClear` removes these records.

Snapshots contain `res_id`, `path`, `type`, `hash`, `status`, and `errors`. They are stored before the terminal notification; its JSON equals the query result. Each load retains its own record, so subsequent loads do not overwrite earlier diagnostics.

`errors` is an array of objects with stable machine-readable `code` values: `path_not_found`, `json_read_failed`, `invalid_pipeline_root`, `empty_node_name`, `duplicate_node`, `invalid_node`, `node_reference_not_found`, `invalid_regex`, `inference_backend_unavailable`, and `load_failed`. `json_read_failed` covers both file-reading and JSON/JSONC parsing failures; it does not distinguish them. `load_failed` is used when the underlying component cannot provide a more specific reason.

`file`, `node`, `pointer`, `field`, and `target` are provided only when their source is known. `pointer` uses JSON Pointer escaping; missing references point to the declaring `next` / `on_error` field. Inherited fields retain the original file location; runtime overrides do not invent a source location. This API preserves existing loading, validation and partial-failure behavior and does not promise an exhaustive list of errors.
For per-instance image budgets and execution-time configuration snapshots, see [Runtime evidence capture](2.5-RuntimeEvidence.md).

The runtime extension APIs use MaaAgent protocol version 9. Upgrade AgentClient and AgentServer together; mismatched versions fail during connection instead of accepting unsupported remote requests.
