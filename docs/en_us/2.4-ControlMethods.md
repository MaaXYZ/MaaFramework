# 2.4 Control Methods

This document provides detailed explanations of the various Screencap (screenshot) and Input (control) methods in MaaFramework and their configurations.

> [!TIP]
>
> - For APIs, screencap/input uses `int` type (bitwise OR combination); for [ProjectInterface V2](3.3-ProjectInterfaceV2.md), use `string` type (use the name directly).
> - [ProjectInterface V2](3.3-ProjectInterfaceV2.md) supports configuring screencap/input methods for Win32, MacOS, Linux, and other controllers. For Adb controllers, screencap/input uses `MaaToolkitAdbDeviceFind` to automatically detect and select the optimal method, no manual configuration required.

## iOS

The iOS controller uses MaaFramework's CoreDevice/DDI implementation to connect to physical iPhones and iPads.

### iOS Screencap

> See `MaaIOSScreencapMethod` in [MaaDef.h](https://github.com/MaaXYZ/MaaFramework/blob/main/include/MaaFramework/MaaDef.h)

As with the Android controller, capture methods form a bitmask and may be combined with bitwise OR. ProjectInterface separates names with `|` or `,`. Both are allowed by default: video is preferred when usable, with screenshot-service fallback.

| Name | API value | Image | Behavior |
| --- | --- | --- | --- |
| Stream | `1` | Decoded HEVC video, lossy | Continuously receives video and obtains an available frame; selecting only this method disables screenshot-service fallback |
| ScreenshotService | `2` | PNG, lossless | Requests a screenshot RPC for each image; selecting only this method starts no video or background video decoder |

Video generally has lower latency; the PNG service suits pixel-exact matching. Timing depends on device, network and image content; historical protocol measurements do not establish performance for every controller/device combination. The decoder handles HEVC frames exceeding the early VideoToolbox length limitation; recoverable packet loss requests keyframes and can rebuild the stream.

Each delivered image retains its own dimensions and orientation. Touch mapping uses that snapshot instead of reading later orientation updates. PNG images are already upright and must not be rotated again. A geometry change during a screenshot request fails that capture and should be retried. Unknown orientation or inconsistent dimensions never produces guessed touch coordinates.

### iOS build and APIs

The iOS controller is disabled by default; enable it with `-DWITH_IOS_CONTROLLER=ON`. See [Building iOS support](4.1-BuildGuide.md#building-ios-support) for dependencies, test switches and distribution packaging.

MaaToolkit implements discovery, pairing, connection checks and DDI preparation. MaaIOSControlUnit implements device sessions, capture, input and app control.
See [MaaToolkitIOSDevice.h](2.2-IntegratedInterfaceOverview.md#maatoolkitiosdeviceh) for the C API.
Python provides `Toolkit.ios_discover`, `ios_pair`, `ios_check_connection` and `ios_prepare`; `ios_pair` returns `(status, IOSWiFiPairing)`.
NodeJS exposes discovery/controller bindings; use C/Python for interactive management. See [iOS device management callbacks](2.3-CallbackProtocol.md#ios-device-management-callbacks) for progress, PIN and cancellation semantics.

### iOS Device Preparation

The controller is available in macOS, Linux, Windows and Android builds with the iOS module enabled. The device requires Developer Mode, trust, pairing and a suitable mounted Developer Disk Image (DDI). No jailbreak, WebDriverAgent or automation app installed on the phone is needed. Linux/Windows USB access additionally requires working usbmux/Apple device drivers.

Use MaaToolkit for discovery, pairing, connection checks and DDI preparation. Pairing returns an owned `MaaIOSWiFiPairing`. Controller creation, connection checks and DDI preparation require an explicit nonempty UDID. The controller receives raw credentials and an Auto/USB/WiFi connection method for that device. Discovery and first pairing can omit the UDID and return it in their results. Toolkit provides optional parsing/formatting of the `MaaIOS1` persistence format; discovery receives a list of structured credentials, while connection checks and DDI preparation receive one target credential. Pairing does not take an existing credential. All operations use the same Auto/USB/WiFi modes. No default pairing directory is read or written. DDI persistent caching is optional: omit `cache_directory` for temporary files, or set it for reusable validated downloads. See [iOS pairing examples](2.2-IntegratedInterfaceOverview.md#ios-pairing-examples) for C/Python usage and callback ownership.

### iOS pairing in PiCli

In the iOS controller configuration, choose USB or Wi-Fi pairing:

- USB: connect and unlock the phone, then accept its trust or pairing prompts.
- Wi-Fi: use the same LAN, select the computer under Settings > Privacy & Security > Developer Mode, and enter the one-use code shown in the terminal.

After `Pairing saved to PiCli configuration.`, credentials are stored in `ios.pairing_records` in `config/maa_pi_config.json` under the runtime directory. Choose `Use existing pairing` on subsequent runs. Failed pairing leaves existing credentials unchanged.
If pairing was revoked on the phone, choose `Clear all local pairing credentials` and confirm before pairing again. This removes credentials for all devices saved by PiCli; it does not revoke authorization on the phone.
Pairing alone does not trigger DDI preparation.

### Automatic DDI preparation in PiCli

Before running iOS tasks, PiCli calls `MaaToolkitIOSDevicePrepare` and proceeds to controller creation and connection only on success. It reuses a confirmed suitable mounted image or performs the required download, installation and mount verification. Preparation errors stop the run; PiCli does not explicitly replace an existing image.

PiCli uses the current user's persistent cache directory:

| Platform | Default directory |
| --- | --- |
| macOS | `~/Library/Caches/MaaPiCli/ddi/` |
| Linux | `$XDG_CACHE_HOME/MaaPiCli/ddi/`; uses `~/.cache/MaaPiCli/ddi/` when unset or not absolute |
| Windows | `%LOCALAPPDATA%/MaaPiCli/cache/ddi/` |

Configure these fields in the `ios` section of `config/maa_pi_config.json`:

```json
{
    "prepare_ddi": true,
    "ddi_cache_directory": "",
    "ddi_download_timeout_seconds": 300
}
```

`prepare_ddi: false` skips preparation; the caller must ensure the device is already prepared, including for offline use. Empty `ddi_cache_directory` selects the platform default; an override must be absolute. The download timeout accepts 1–3600 seconds and defaults to 300.
Cached assets avoid repeat downloads, but personalization may require network access. During preparation, Ctrl+C requests cancellation. After cleanup, interactive mode returns to the menu; direct mode follows the existing task-failure exit path. Underlying operations respond at their cancellation checkpoints. These defaults belong to PiCli; Toolkit callers choose their own cache location or temporary storage.

### Input and capability boundaries

- Native input uses the device HID service. There is one implemented input backend, without an artificial input-method enum. Single-finger click/swipe and down/move/up with `contact=0` are supported; other contacts, scrolling, relative movement and Shell are unsupported.
- `click_key`, `key_down` and `key_up` use Android keycodes. Mapped keyboard keys, left/right modifiers and Home (`3`), lock (`26`), volume (`24`/`25`) and mute (`164`) hardware buttons are supported; unmapped keys fail explicitly. `inactive` and destruction attempt to release held input.
- `input_text` accepts nonempty US-layout ASCII, tab and newline. A string containing Chinese, other Unicode or unsupported control characters is rejected in full before sending any key. Characters are never silently skipped or pasted automatically. The phone's current input method determines how physical keystrokes become text.
- `start_app`/`stop_app` take a Bundle Identifier. Starting foregrounds an existing instance without killing it first. Stopping terminates the app's processes and succeeds when none were running.
- Media capability is determined by device replies. Streaming has been verified on iPhone14,4/iOS 27. Protocol validation on iPad11,2/iPadOS 18.7.8 supports screenshots and HID but rejects streaming. Prefer `ScreenshotService` on older systems; verify service availability for other models and OS versions.
- Locked or sleeping devices may return a black screenshot; this does not establish a template failure. Home can wake the device. Images may be returned without orientation metadata, but touch mapping for such images cannot be promised.
- Another client may replace the device's media stream. Avoid running multiple mirroring/control clients on the same device simultaneously.

### iOS Freeform Example

The runnable configuration and resources are in [`sample/ios/`](../../sample/ios/).

This example uses only pipelines and runs in PiCli. Python, agents and custom actions are not required.
Build MaaFramework/PiCli with iOS support, install Freeform and keep the device unlocked in portrait orientation.

Run from the repository root (macOS `RelWithDebInfo` build):

```bash
cp sample/ios/interface.json build/bin/RelWithDebInfo/interface.json
cp -R sample/ios/resource build/bin/RelWithDebInfo/
cd build/bin/RelWithDebInfo
./MaaPiCli
```

Back up existing interface or same-named resource files, or use a separate runtime directory.
The copy commands do not overwrite configuration or credentials in `config/`.

Pair the device using the [PiCli pairing flow](#ios-pairing-in-picli), then select and run a task.

#### Example tasks

- `iOS screenshot check`: captures a frame without tapping the device. Success only means a nonempty image was returned.
- `Freeform Apple drawing`: launches Freeform, recognizes drawing controls, draws the body and leaf using two continuous polyline `Swipe` actions, and confirms the ink. It modifies the canvas and is not selected by default.

The controller scales the short side to 720; templates, UI coordinates and strokes target a portrait image
of approximately 720×1568. Other devices, orientations or OS versions may require adjustment.
Each stroke keeps the finger down through its waypoints, lifting between the two strokes.
Outline points derive from the simple-icons Apple icon (CC0-1.0).
Task success indicates recognition/action completion; it does not compare before/after pixels to verify the drawing.

## Android Native

The Android native controller uses `MaaAndroidNativeControlUnit` for direct screenshot and input on Android.

### Android Native Prerequisites

1. Android platform only

### Android Native Configuration

Pass a JSON config to `MaaAndroidNativeControllerCreate(config_json)`:

- `library_path`: Android native control unit library path
- `screen_resolution.width` / `screen_resolution.height`: raw screenshot resolution, also used as the touch coordinate space
- `display_id`: target display id, optional, defaults to `0`
- `force_stop`: whether to force stop before `start_app`, optional, defaults to `false`

> [!NOTE]
>
> MaaFramework converts scaled recognition coordinates back to raw screenshot coordinates in `ControllerAgent`.  
> The Android native controller no longer performs any frame-to-touch remapping internally, and only clamps to `screen_resolution`.  
> If the control unit reports a raw frame resolution different from `screen_resolution`, screencap fails immediately.

### Android Native Input

Multi-touch is supported. `contact` is the finger id (0 for the first finger, valid range 0–15, matching Android MotionEvent pointer id).  
`Click` / `LongPress` / `Swipe` / `MultiSwipe` / `TouchDown` / `TouchMove` / `TouchUp` can use different `contact` values to distinguish fingers.

> [!NOTE]
>
> The external control unit library's `TouchArgs` must include a `contact` field, otherwise multi-touch events cannot be delivered correctly.  
> `pressure` is currently not forwarded to the external library.

## Win32

### Win32 Input

> Reference: [MaaDef.h](https://github.com/MaaXYZ/MaaFramework/blob/main/include/MaaFramework/MaaDef.h#L326-L374)

Select one of the values below.

No default value. Client can choose one as the default.

Different programs on Win32 handle input differently, so there is no universal method.

| Name | API Value | Compatibility | Requires Admin | Seizes Cursor | Background | Description |
| --- | --- | --- | --- | --- | --- | --- |
| Seize | `1` | High | No | Yes | No | |
| SendMessage | `2` | Medium | Maybe | No | Yes | |
| PostMessage | `4` | Medium | Maybe | No | Yes | |
| LegacyEvent | `8` | Low | No | Yes | No | |
| PostThreadMessage | `16` | Low | Maybe | No | Yes | Deprecated |
| SendMessageWithCursorPos | `32` | Medium | Maybe | Brief | Yes | Briefly moves cursor to target position then restores, for apps that check real cursor position |
| PostMessageWithCursorPos | `64` | Medium | Maybe | Brief | Yes | Briefly moves cursor to target position then restores, for apps that check real cursor position |
| SendMessageWithWindowPos | `128` | Medium | Maybe | No | Yes | Briefly moves window to align target with cursor then restores, does not seize mouse |
| PostMessageWithWindowPos | `256` | Medium | Maybe | No | Yes | Briefly moves window to align target with cursor then restores, does not seize mouse |
| Interception | `512` | Medium | Yes | No | No | Injects mouse and keyboard events through the Interception driver when normal Win32 injection paths do not work |
| AnchoredTouch | `1024` | Medium | Maybe | No | Yes | Injects synthetic touch points, the target window receives `WM_POINTER` messages, mouse only |

> [!NOTE]
>
> - Admin privileges mainly depend on the target program's permission level. If the target program runs as administrator, running with admin privileges is required for compatibility.
> - The `WithCursorPos` methods briefly move the cursor to the target position, then restore it after sending the message, hence "Brief" cursor seizure, but it does not block user operations.
> - The `WithWindowPos` methods briefly move the window so the target position aligns with the current cursor position, then restore the window position after sending the message. The cursor is not moved, so there is no mouse seizure, but the window may briefly flicker.
> - `Interception` requires the Interception driver to be installed correctly, and the process usually needs the same or higher privilege level as the target application.
> - `Interception` sends mouse and key operations through the driver. Text input still uses system Unicode `SendInput` and does not go through the Interception driver path.
> - `AnchoredTouch` injects synthetic touch points through `InjectSyntheticPointerInput`, requires Windows 10 1809 or later. It never moves the cursor and never changes the foreground window, so it does not interfere with the user's work in other windows, and applications that render according to the cursor position are not affected. The cost is a brief visible change on the target window itself while it is occluded, see the next entry.
> - `AnchoredTouch` implements clicking and swiping only. Keyboard operations can be routed to another method, but `scroll` has **no alternative**: scrolling always goes through the mouse method, and a synthetic touch device cannot express a wheel. Choose another input method entirely if you need scrolling.
> - Synthetic pointers are dispatched by the desktop Z-order, so `AnchoredTouch` briefly raises the target window to topmost with the lowest layered alpha while the target point is occluded, and restores the original Z-order and alpha once all contacts are released. A partially visible target window flickers for about 70ms per operation. If raising does not take effect, the operation fails instead of injecting into the window that occludes the target.
> - Raising requires the `WS_EX_LAYERED` extended style on the target window. It is added on the first raise, verified before every raise, and removed when the controller goes idle or `inactive` is called, unless another module is relying on that layered state by then, in which case the style is kept. If the target point is never occluded, no state of the target window is touched at all. If the style cannot be kept or the opacity cannot be lowered, the operation fails rather than raising the target window visibly. Windows that are layered via `UpdateLayeredWindow` are refused, since touching them would break their painting. `WS_EX_LAYERED` is documented as incompatible with `CS_OWNDC` and `CS_CLASSDC` window classes, but that restriction does not always hold in practice (Unity windows carry `CS_OWNDC` and work), so such classes only produce a warning and the actual API results decide.
> - A minimized target window is not supported, the operation fails with an error: the client area of a minimized window is off-screen and raising does not change that. With the `FramePool` / `PrintWindow` screencap methods the window is taken out of the minimized state before every capture, so this does not occur; with the other screencap methods a minimized window cannot be captured either. Note that the pseudo-minimize of those two methods restores the style and opacity on `inactive` without minimizing the window again.
> - While the window is borrowed, `WS_EX_TRANSPARENT` is temporarily removed, since it lets input pass through to the windows underneath, and restored afterwards. Because the screencap-side pseudo-minimize writes the same window's extended style and opacity, `AnchoredTouch` verifies before restoring that these attributes still match what it wrote; if they do not, the window is treated as taken over by another module and the old values are not written back, so whatever that module just configured is left intact. This check cannot fully eliminate the window in which the two sides interleave.
> - Interception keyboard selection excludes slots without a hardware ID. Automatic selection keeps an attached keyboard bound, or chooses the lowest attached slot when no valid binding remains. This does **not** identify the keyboard the user last typed on. For multiple keyboards, set `MAA_INTERCEPTION_KEYBOARD_DEVICE` in the host application's environment before launching it: use a zero-based slot (`0`–`9`) or the exact first hardware ID reported in the device initialization log. A hardware ID can follow a keyboard across slot changes; identical devices may share an ID. An unavailable explicit selection fails rather than falling back to another keyboard.
> - Keyboard attachment is rechecked before input. Selection changes are deferred until all keys held by the controller have been released. If the bound keyboard disappears while a key is held, release fails rather than sending the release to a replacement device. Stop/reconnect the controller after an input failure. Driver write success alone does not guarantee the target application consumed the event.
> - Win32 also provides a **Mouse Lock Follow** mode: enable with `MaaControllerSetOption(ctrl, MaaCtrlOption_MouseLockFollow, &enabled, sizeof(bool))` (set `enabled` to `true` to enable, `false` to disable). Designed for TPS/FPS games that lock the mouse to the window in the background. When enabled, the window continuously follows the mouse cursor, and RawInput counter-moves prevent the game from sensing hardware mouse movement. Use `MaaControllerPostRelativeMove` to inject intentional camera rotation while this mode is active. **Note:** On Win32, `MaaControllerPostRelativeMove` requires mouse-lock-follow mode to be active; calling it without this mode will fail. Only supported with MessageInput-based input methods (SendMessage / PostMessage variants).
> - Win32 also provides a **Background Managed Keys** guardian: declare the managed key domain through `MaaControllerSetOption(ctrl, MaaCtrlOption_BackgroundManagedKeys, keycodes, sizeof(int32_t) * count)` with an array of virtual key codes to manage. After setting, matching key operations automatically route through the background guardian path and continuously correct key state while the controller is idle.

### Win32 Screencap

> Reference: [MaaDef.h](https://github.com/MaaXYZ/MaaFramework/blob/main/include/MaaFramework/MaaDef.h#L295-L325)

Combine the selected methods below using **bitwise OR** to provide a single value. MaaFramework will try all provided methods and select the fastest available method.

No default value. Client can choose one combination as the default.

Different programs on Win32 handle rendering differently, so there is no universal method.

| Name | API Value | Speed | Compatibility | Requires Admin | Background | Description |
| --- | --- | --- | --- | --- | --- | --- |
| GDI | `1` | Fast | Medium | No | No | |
| FramePool | `2` | Very Fast | Medium | No | Yes | Available on Windows 10 1903+ |
| DXGI_DesktopDup | `4` | Very Fast | Low | No | No | Desktop duplication (full-screen output copy) |
| DXGI_DesktopDup_Window | `8` | Very Fast | Low | No | No | Desktop duplication cropped to window |
| PrintWindow | `16` | Medium | Medium | No | Yes | |

> [!NOTE]
>
> Three predefined combination macros are provided:  
>
> - `MaaWin32ScreencapMethod_All`: all screencap methods  
> - `MaaWin32ScreencapMethod_Foreground`: `DXGI_DesktopDup_Window | ScreenDC`  
> - `MaaWin32ScreencapMethod_Background`: `FramePool | PrintWindow`  
>
> FramePool and PrintWindow have built-in pseudo-minimize support: when the target window is minimized, they make it transparent and click-through, then restore it without activation, allowing screencap to continue without disturbing the user.  
> Other screencap methods will fail when the target window is minimized. Please avoid minimizing the window when using those methods.

#### Screencap

##### Wlr

When using `Wlr` screencap method, the wlroots compositor must support the following protocols:

- Wayland core protocol
- `wlr-screencopy-unstable-v1`

##### PipeWire

When using `PipeWire` screencap method, there are two modes:

- **Monitor capture**: pass the compositor's PipeWire FD (`pw_socket_fd`) and node ID (`pw_node_id`)
  obtained from `xdg-desktop-portal`.
- **Session-daemon node capture**: no FD; set `pw_node_id` to attach to a node on the session PipeWire daemon
  (e.g. gamescope's Video/Source node). Discover gamescope node IDs with `MaaToolkitGamescopeInstanceFindAll`.

In [ProjectInterface V2](3.3-ProjectInterfaceV2.md), select the mode via `controller.linux.pipewire_source`:
`Portal` corresponds to monitor capture, `Gamescope` to session-daemon node capture (default `Gamescope`).

#### Input

##### Wlr

When using `Wlr` input method, the wlroots compositor must support the following protocols:

- Wayland core protocol
- `virtual-keyboard-unstable-v1`
- `wlr-virtual-pointer-unstable-v1`

> [!NOTE]
>
> It is recommended to start a nested compositor session when using `Wlr` input method. It is not recommended to control
> the compositor managing the current desktop, as this may cause unexpected behavior during task execution.

##### Libei

When using `Libei` input method, `eis_socket_path` must point to the EIS socket provided by the compositor, e.g.
gamescope's `/run/user/<uid>/gamescope-<n>-ei`. Text input requires `libei >= 1.6.0` on the system.

##### UInput

When using `UInput` input method, the current user must have read/write permission for the `/dev/uinput` device.

### Key Codes

In the Linux controller configuration of [ProjectInterface V2](3.3-ProjectInterfaceV2.md), set `use_win32_vk_code` to `true` to use Win32 Virtual-Key codes (VK_*). The default value is `false`, which uses Linux evdev scan codes.
