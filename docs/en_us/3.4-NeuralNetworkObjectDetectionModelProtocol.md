# Neural-network object-detection model protocol

`NeuralNetworkDetect` loads object-detection models through ONNX Runtime. The ONNX model supplies tensor structure and metadata. A same-name JSON file describes image preprocessing, output decoding, and NMS semantics that cannot be expressed by the model graph.

## 1. Supported behavior

- The input consists of one three-channel image tensor in RGB or BGR order and NCHW or NHWC layout. An INT64 `[1, 2]` auxiliary input containing the original image size may also be used. Runtime batch is fixed at 1, while H/W may be static or dynamic.
- FP32 and FP16 image inputs and floating-point outputs are supported. Preprocessing uses FP32, and FP16 outputs are converted to FP32 before decoding. QDQ INT8 models whose graph inputs and outputs remain floating-point can be used directly.
- Input processing covers stretch resize, aspect-ratio-preserving padding, color-order conversion, scalar scaling, three-channel mean/std normalization, and NCHW/NHWC layout conversion.
- Outputs may use one ChannelsFirst or ChannelsLast tensor, or multiple Split tensors, combining boxes, class scores, objectness, final scores, and class IDs.
- Boxes may use `CxCyWh` or `XyXy` in input-image, normalized, or original-ROI coordinates. Class-score processing covers no activation, Sigmoid, Softmax, objectness multiplication, a no-object channel, and global top-k selection.
- NMS supports `None`, class-aware IoU suppression through `ClassAwareIoU`, and `CandidateCoverage` for Maa's established behavior.

Each ROI is preprocessed, inferred, coordinate-restored, validated, and NMS-filtered independently before its results are merged into the Pipeline result. See [`NeuralNetworkDetect` in the Pipeline protocol](3.1-PipelineProtocol.md#neuralnetworkdetect) for `threshold`, `multi_label`, `expected`, `order_by`, and `index`.

## 2. Resolution behavior and configuration precedence

For `foo.onnx`, MaaFramework looks for `foo.json` in the same directory. The final contract is resolved in this order:

1. **ModelProto**: input/output names, element types, shapes, and static input dimensions. Neither JSON nor metadata can override them.
2. **Valid Ultralytics metadata**: determines input processing, output decoding, NMS, dynamic input size, and labels.
3. **Explicit JSON steps**: entries with `type` in `input` and `output`.
4. **JSON presets**: expanded into input or output steps.
5. **Step defaults**: parameters omitted from an explicit step use that step's defaults.

Metadata and JSON may describe the same configuration. When metadata determines a complete input or output contract, it controls that side; conflicting complete JSON configuration is ignored with a warning. A metadata field that cannot be parsed is treated as missing, so JSON can supply the corresponding information. For example, JSON `Resize.size` may supply the size when metadata has no valid `imgsz`. If metadata cannot determine the output contract, JSON `output` must provide a complete set of output steps.

JSON must satisfy the schema. Unknown fields, duplicate stages, invalid parameters, and incomplete contracts produce `ModelError`. MaaFramework matches the image input, auxiliary input, and output tensors from ModelProto. Zero matches or multiple matches also produce `ModelError`. JSON cannot configure tensor names, element types, shapes, or static input dimensions, and MaaFramework does not infer unknown processing semantics from filenames or shapes.

Dynamic width and height are resolved independently in this order:

1. A static ModelProto dimension.
2. Pipeline `input_size`.
3. Ultralytics metadata `imgsz`.
4. JSON `Resize.size`.
5. The current ROI dimension.

Both `input_size` and `Resize.size` use `[width, height]` order and fill dynamic dimensions only. The current ROI size is used without automatic stride alignment.

Labels are selected in this order: `Pipeline labels > metadata names > JSON labels > Unknown_<class_id>`. Pipeline and JSON labels accept string arrays; JSON also accepts an object whose class-ID keys are contiguous from 0. When the output determines the class count, the label count must match it.

## 3. Ultralytics models that do not need JSON

Models exported with the [NNDetect Recipe](https://github.com/MaaXYZ/MaaNeuralNetworkCookbook/tree/main/NeuralNetworkDetect), or through Ultralytics [`model.export(format="onnx")`](https://docs.ultralytics.com/modes/export/), can omit the same-name JSON when their ONNX metadata contains `author=Ultralytics`, `task=detect`, and a `Detect` or `RTDETRDecoder` head.

Common examples include YOLOv8, YOLO11, YOLO26, and RT-DETR from Ultralytics. MaaFramework reads metadata such as `head`, `end2end`, `args.nms`, `imgsz`, and `names`, then validates the automatically generated contract against ModelProto I/O.

| Metadata capability | Automatic input contract | Automatic output contract | NMS |
| --- | --- | --- | --- |
| `head=Detect`, Dense output | `UltralyticsLetterbox` | `YoloDense` | `ClassAwareIoU`, threshold 0.7 |
| `head=Detect`, end-to-end or exported with `nms=true` | `UltralyticsLetterbox` | `YoloEndToEnd` | `None` |
| `head=RTDETRDecoder` | `Resize` | `DetrPacked`, normalized `CxCyWh` | `None` |

For `Detect`, MaaFramework first uses valid `end2end` and `args.nms` metadata. If these fields do not determine the output, the ModelProto tensor contract must uniquely match either Dense or end-to-end output. Both YOLO26's default end-to-end output and a Dense export with `end2end=false` are resolved automatically.

Models within these automatic profiles normally need no JSON. If JSON is present, metadata-determined input, output, and NMS semantics still take precedence. The JSON fields below are primarily for object-detection models outside the automatic profiles, or models whose missing metadata cannot form a complete contract.

## 4. JSON fields, presets, and parameter overrides

The same-name JSON has the following top-level structure:

```json
{
  "$schema": "https://raw.githubusercontent.com/MaaXYZ/MaaFramework/main/tools/neural-network-detector.schema.json",
  "input": [
    { "preset": "Resize" }
  ],
  "output": [
    { "preset": "YoloDense" }
  ],
  "nms": { "type": "ClassAwareIoU", "threshold": 0.7 },
  "labels": ["Cat", "Dog"]
}
```

| Field | Meaning |
| --- | --- |
| `$schema` | Optional schema URL. |
| `input` | Array of input-processing steps. |
| `output` | Array of output tensor-mapping and decoding steps. |
| `nms` | NMS type and threshold. |
| `labels` | Optional label array, or an object numbered contiguously from class 0. |

### 4.1 Presets and explicit steps

`input` and `output` may each contain at most one `preset` and at most one step of each `type`. Array order does not control execution; stages run in a fixed order. MaaFramework expands the preset first and then applies explicit steps, so an explicit step replaces the corresponding preset stage.

Replacement covers the entire stage. Parameters omitted from an explicit step use that step's own defaults; they do not inherit values from the corresponding preset stage. For example, `DetrQueries` provides a `ScoreDecode` stage with Sigmoid. If an explicit `ScoreDecode` is added to set `no_object_index`, it must also include `"activation": "Sigmoid"`; otherwise that explicit stage uses the default `None` activation.

When metadata has already determined the input or output contract, metadata takes precedence over both explicit JSON steps and presets.

### 4.2 Input steps

| Stage | Parameters | Defaults |
| --- | --- | --- |
| `Resize` | `mode`: `Stretch` / `Letterbox`; optional `size`, `interpolation`, `fill`, and `padding_position` | `Stretch`, `Linear`, fill 114, `Center` |
| `Color` | `order`: `RGB` / `BGR` | `RGB` |
| `Scale` | `factor` | `1 / 255` |
| `Normalize` | Three-channel `mean` and `std` | Both are required when the stage is present. |
| `Layout` | `order`: `NCHW` / `NHWC` | `NCHW` |
| `AuxInput` | `kind`: `OriginalSize`; `order`: `HW` / `WH` | `OriginalSize`, `HW` |

Input presets expand as follows:

| Preset | Expanded processing |
| --- | --- |
| `UltralyticsLetterbox` | Aspect-ratio-preserving centered padding with 114, RGB, divide by 255, NCHW |
| `Resize` | Stretch resize, RGB, divide by 255, NCHW |
| `ResizeIN` | `Resize`, followed by ImageNet mean/std normalization |

Without a preset, a complete input contract contains `Resize`, `Color`, `Scale`, and `Layout`. Add `Normalize` and `AuxInput` as required by the model.

### 4.3 Output steps

| Stage | Parameters and behavior |
| --- | --- |
| `TensorMap` | `layout` is `ChannelsFirst`, `ChannelsLast`, or `Split`; `fields` declares tensor-field roles. |
| `BoxDecode` | `format` is `CxCyWh` or `XyXy`; `coordinates` is `Input`, `Normalized`, or `Source`. |
| `ScoreDecode` | Configures class and objectness activation, score combination, and the no-object channel. |
| `CandidateSelect` | Optional `top_k` for global candidate selection. |

`TensorMap.fields` supports `Boxes`, `ClassScores`, `Objectness`, `Score`, and `ClassId`. The contract must contain `Boxes` and use one of these scoring structures:

- `ClassScores`, optionally together with `Objectness`;
- `Score` together with `ClassId`.

`ChannelsFirst` maps one `[1, F, N]` floating-point tensor, while `ChannelsLast` maps one `[1, N, F]` floating-point tensor. `Split` matches one independent tensor for each field by role, element type, and shape rather than output name. `ClassId` may use INT64 or a floating-point value that exactly represents a non-negative integer.

`BoxDecode.coordinates=Input` and `Normalized` restore boxes through the input preprocessing transform. `Source` indicates that boxes already use the current ROI's original coordinates.

`ScoreDecode.activation` supports `None`, `Sigmoid`, and `Softmax`; `objectness_activation` supports `None` and `Sigmoid`; `combine` supports `None` and `Multiply`. `no_object_index` may be `First`, `Last`, or a non-negative integer. A Softmax denominator still contains the no-object channel; emitted class IDs skip that channel and are renumbered contiguously. `activation=None` requires input scores that are already in `[0, 1]`.

`CandidateSelect.top_k` must be a positive integer. With Pipeline `multi_label=true`, global top-k covers every proposal/query and class pair. With `false`, the highest-scoring class is selected for each proposal/query before global top-k. Outputs that already carry `ClassId` are unaffected by `multi_label`. Candidate selection runs before NMS; they are separate stages.

Output presets expand as follows:

| Preset | Expanded processing | Default NMS |
| --- | --- | --- |
| `YoloDense` | ChannelsFirst; `Boxes + ClassScores`; input-pixel `CxCyWh`; activated scores | `ClassAwareIoU`, threshold 0.7 |
| `YoloEndToEnd` | ChannelsLast; `Boxes + Score + ClassId`; input-pixel `XyXy` | `None` |
| `DetrQueries` | Split; `Boxes + ClassScores`; normalized `CxCyWh`; Sigmoid; top-k 300 | `None` |
| `DetrPacked` | ChannelsLast; `Boxes + Score + ClassId`; normalized `CxCyWh` | `None` |

Without a preset, a complete output contract contains `TensorMap`, `BoxDecode`, and `ScoreDecode`. Add `CandidateSelect` as required by the model.

### 4.4 NMS and labels

`nms.type` supports `None`, `ClassAwareIoU`, and `CandidateCoverage`. Within JSON, the policy is selected in this order: top-level `nms` > output preset's default NMS > `None`. Automatically resolved metadata NMS still takes precedence over all three. The default `threshold` for `ClassAwareIoU` and `CandidateCoverage` is 0.7. `threshold` is ignored when `type` is `None`. Explicit output steps do not clear the output preset's default NMS; use top-level `nms` to change it.

`labels` may be an array:

```json
{ "labels": ["Cat", "Dog"] }
```

It may also be an object with keys numbered contiguously from 0:

```json
{ "labels": { "0": "Cat", "1": "Dog" } }
```

Labels must be non-empty and unique. Metadata `names` takes precedence over conflicting JSON `labels`, and MaaFramework records a warning.

## 5. RF-DETR reference configuration

An RF-DETR ONNX export commonly has one image input and separate `dets` and `labels` outputs for boxes and class scores. MaaFramework uses their element types and shapes to validate a selected contract. However, `rfdetr_notes`, tensor names, and shapes do not by themselves determine preprocessing, coordinate format, score activation, or candidate selection, so a same-name JSON file is required.

For example, if the RF-DETR Nano model is stored at `model/detect/rfdetr_nano.onnx`, create `model/detect/rfdetr_nano.json`:

```json
{
  "$schema": "https://raw.githubusercontent.com/MaaXYZ/MaaFramework/main/tools/neural-network-detector.schema.json",
  "input": [
    { "preset": "ResizeIN" }
  ],
  "output": [
    { "preset": "DetrQueries" },
    { "type": "ScoreDecode", "activation": "Sigmoid", "no_object_index": "Last" }
  ],
  "nms": { "type": "None" }
}
```

The corresponding Pipeline node may be written as:

```jsonc
{
  "recognition": "NeuralNetworkDetect",
  "model": "rfdetr_nano.onnx",
  "multi_label": false,
  "threshold": 0.3
}
```

The configuration means:

- `ResizeIN` supplies stretch resize, RGB, division by 255, and ImageNet mean/std normalization.
- `DetrQueries` supplies Split `Boxes + ClassScores`, normalized `CxCyWh`, Sigmoid, and top-k 300.
- The explicit `ScoreDecode` replaces the preset stage, preserving Sigmoid while marking the last class-score channel as no-object.
- `nms=None` disables external NMS. It is also the default NMS for `DetrQueries`, but remains in the example to make the model behavior explicit.
- `multi_label=false` chooses the highest-scoring class for each query before global top-k. `threshold` remains a Pipeline setting.

This JSON relies on ModelProto to match `dets` and `labels`; output tensor names neither need nor may be configured. Loading produces `ModelError` when a complete `input` or `output` contract is missing. RF-DETR export variants may have different graph contracts, so the configuration must still match the actual model I/O.
